# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

SpendSync is an expense tracker: a native Android client (`app/`) talking to a Next.js + Better Auth + Postgres API (`backend/`). The Android app points at the deployed API (`API_BASE_URL` in `app/build.gradle.kts`, currently `https://spend-sync-api.vercel.app`), not localhost.

## Android app (repo root, Gradle)

```
./gradlew assembleDebug                      # build
./gradlew testDebugUnitTest                  # JVM unit tests (app/src/test)
./gradlew testDebugUnitTest --tests "com.example.spendsync.utils.AmountMaskingTest"   # single class
./gradlew connectedDebugAndroidTest          # instrumented tests (needs device/emulator)
```

Kotlin + Jetpack Compose (Material3), Retrofit/OkHttp/Gson, DataStore, WorkManager, Coil. Java 17, minSdk 24, package `com.example.spendsync`. No ViewModels/DI framework in the main flow: screens receive repositories (`AuthRepository`, `FinanceRepository`) and shared state holders directly.

### Architecture
- `data/remote` — Retrofit services (`AppApiService`, `AuthApiService`), `AuthInterceptor` attaches the Better Auth **bearer token**; `AuthEvents` signals session expiry. DTOs in `data/remote/model`.
- `data/repository` — `FinanceRepository` wraps API calls; `SettingsSync` syncs user settings with the backend. `data/local/SessionDataStore` persists the session/token and local prefs.
- `ui/main/MainScreen` hosts the bottom-nav tabs (Home, Holds, Analytics, Budget, Profile) in a pager; `ui/shared` holds cross-tab state (`DateFilterState`, `AmountVisibilityState`, PIN dialogs). Analytics/Budget currently live in `ui/placeholder`.
- **Amount masking / PIN privacy**: amounts are hidden by default behind a PIN; `AmountVisibilityState` runs an auto-lock timer, and `utils/AmountMasking.kt` + `PinHashing.kt` implement it. Every screen displaying amounts must go through the masking helpers (see `docs/superpowers/specs/2026-08-05-amount-masking-design.md`).
- `notifications/` — auto-capture of transactions from bank/UPI notifications: `TransactionNotificationListenerService` → `NotificationTransactionParser` (filtered by `NotificationAppAllowlist`) → `PendingCapture` queued and retried by `PendingCaptureRetryWorker`; `Hold*` classes schedule hold-reminder notifications.
- `crash/CrashHandler` is installed in `SpendSyncApp` and shows `ErrorActivity` instead of the system crash dialog.

Design specs and implementation plans for features live in `docs/superpowers/{specs,plans}/` — read the relevant one before changing money-hold, notification capture, or amount masking.

### Architecture
- **`backend/README.md` is stale** — it describes an Express server (`server.ts`, `controllers/`, `middleware/`). The code is now Next.js App Router: endpoints are `src/app/api/**/route.ts`.
- Every route export is wrapped in `withApi(handler, { auth: 'required' | 'optional' })` from `src/lib/api-handler.ts`, which centralizes rate limiting (in-memory), CORS (allow-list from config), Better Auth session lookup, and error mapping (`ZodError` → 422, `ApiError` → its status). Throw errors from `src/utils/errors.ts`; build responses with `src/lib/response.ts`. Each route file re-exports `corsPreflight as OPTIONS`.
- Layering: `route.ts` (parse/validate with Zod schemas from `src/types/*.types.ts`) → `src/services/*.service.ts` (business logic + Drizzle queries). Domains: transactions, categories, budgets, holds, dashboard, settings.
- Auth: `src/config/auth.ts` (Better Auth, email+password, 7-day sessions, `bearer` plugin for the Android client) mounted at `api/auth/[...all]`. **Forgot password** is our own flow (not Better Auth's link flow): `POST /api/password/forgot` emails a 6-character letters+digits code (`src/password-reset/`, only a keyed hash is stored in `password_resets`, 15 min, 5 tries, 3 requests/hour, always answers the same so it can't reveal who has an account); `POST /api/password/reset` checks it, sets the password with `hashPassword` from `better-auth/crypto` and signs the user out everywhere. Android: log in, sign up and forgot password are pages of ONE screen, `AuthFlowScreen` + `AuthShell` (`ui/auth/`), so switching never re-slides the hero (keep it a single nav destination).
- DB: Drizzle on `postgres`. Runtime imports `src/db/schema/index.ts` (per-domain files), but `drizzle.config.ts` points at the separate monolithic `src/db/schema.ts` — **schema changes must be made in both** or `db:push` will diverge from runtime.

## UI conventions (Android)
- **One component per concept**: buttons are `AppButton`/`AppIconButton`/`AppChip`; dialogs and sheets are `AppDialog`/`AppOptionDialog`/`AppConfirmDialog`/`AppSheet`; text inputs are `AppTextField` (all in `ui/components`). Don't hand-roll `Button`s or dialog cards.
- **Strings**: no literals in UI/notification/repository code — use `tr(R.string.x)` (`ui/i18n`). Languages en/hi/es/fr/de live in `res/values*/strings.xml`; `I18nResourcesTest` enforces matching keys and placeholders. Don't call `tr()` in enum constructors or top-level vals (stale after a language switch). Stored values (theme, accent, categories) are shown through `themeLabel`/`accentLabel`/`categoryLabel`.
- **Loading states**: render the real layout with placeholder data inside `Skeleton(loading) { … }`; import `Text`/`Icon` from `ui.components` (not material3) so they turn into bones.
- **Colours**: theme tokens only (`MaterialTheme.colorScheme`, `incomeColor()`/`expenseColor()`); the app theme follows Settings, not the system, so use `isAppDark()` rather than `isSystemInDarkTheme()`.
- **Settings**: every preference changes through `SettingsSynchronizer.changed(SettingField.X)` (local first, queued retry, server-confirmed). New setting = `SettingField` + `user_settings` column + zod field in `backend/src/types/settings.types.ts` (+ both schema files) + translations.
- Backend schema changes need `npm run db:push` before deploying. `local.properties` must use forward slashes.

## Assistant (chatbot)
- **Backend** (`backend/src/assistant/`): `POST /api/assistant/chat` streams SSE (`loop.ts`, manual tool loop). Models are **free by default** and provider-neutral: `llm/` has adapters (`gemini.ts`, `openai-compat.ts` for Groq/Cerebras/OpenRouter/Mistral, `anthropic.ts` paid + opt-in only), `chain.ts` lists the failover order (override with `ASSISTANT_CHAIN`; a provider is active only if its key is set), `router.ts` does the failover (cool-downs, first-token timeout, mid-answer `reset`, `no_tools` models retried in "context" mode). If every model fails, `fallback.offlineAnswer` answers from the help guide / the user's numbers. `tagfilter.ts` strips fake tool tags/`<think>` from model text. Tools (`tools.ts`) have tiers (`permissions.ts`): `read`, `navigate`, and `propose` run; `propose_entry` only sends a confirm card (the phone saves after Confirm via `ProposalExecutor`); clear-data / sign-out / delete-account have **no tool by design** (tests enforce it). Users can switch tools off and set model/style/tone/instructions (`prefs` in `request.ts`, stored in `user_settings.assistant_*`). Thumbs up/down go to `POST /api/assistant/feedback` (`feedback.ts`; repeated reasons become per-user hints in the prompt). Reports go to `POST /api/support/tickets` (`support/`): saved in `support_tickets` first, then emailed via `lib/email.ts` (nodemailer; env `SMTP_*`, `EMAIL_FROM`, `SUPPORT_EMAIL_TO`); `GET` lists the user's own. `GET /api/assistant/status` feeds the settings screen. Help answers come from `knowledge.ts` BM25 — update `HELP_ENTRIES` when a feature changes. Keys: `backend/.env.example`. Schema changes go in BOTH schema files, then `npm run db:push` (read its data-loss list first). Tests: `npx vitest run`; `npx vite-node scripts/probe-assistant-models.ts` checks the real models.
- **Android** (`data/assistant/`, `ui/assistant/`): `AssistantRepository` streams SSE, `ChatStore` is on-device SQLite history (filtered by user id), `reduceReply` builds the streamed reply, `maskAmountsInText` applies the PIN-masking rule to chat text. Consent is `SessionDataStore.assistantConsent` (device-local); everything else is `AssistantPrefs` (`SettingField.Assistant`, synced) edited in Settings → Assistant (`ui/settings/AssistantPage.kt`). The chat shows which model answered (`source` event) and drops text on `reset`. All assistant strings are in `strings_assistant.xml` + translations.
- Adding a write tool later: tier `write`, enable it in `canRun` only together with a confirm card + undo, and log it in `assistant_audit`.

## Planify (monthly plan, replaces the old Budget page)
- **Backend** (`backend/src/planify/`, routes `api/plans/**`): a plan = `plans` row (income, carry-over) + `budgets` rows as buckets (`kind` fixed/spend/savings, `name`, `sortOrder`, `rollover`). Spent is always derived from transactions. `status.ts` (pure maths: bucket states, safe-to-spend, pace), `suggest.ts` (plan from 3 months of history), `service.ts` (load/save/move). Limits are soft: nothing is ever blocked. Months are UTC half-open ranges. Schema changes go in both schema files.
- **Android**: `data/planify/PlanMath.kt` mirrors the server maths; `PlanAlerts` runs after every created transaction (UI, notification capture, retry worker, assistant) and posts via `notifications/PlanNotifier` (80% / limit / over / pace / salary prompt; each level once per bucket per month, max 3 a day, no amounts while masking is on). `PlanAlertMemory` persists what was already announced. Tapping a notification goes through `PlanifyLinks` to the Planify tab. UI in `ui/planify/`; `PlanBucketLine` is the live line on Add expense.
- **Planify settings** are synced (`SettingField.Planify`; `user_settings.planify_alerts/planify_daily/planify_salary_min`, zod fields, both schema files): Settings → Planify page (`PlanifySettingsPage`). `PlanDailyWorker` (WorkManager, ~8 pm, `sync()` keeps it matching the setting, also on app start) posts the daily summary / month-end wrap-up. Assistant tool `get_plan_status` (read tier) + `open_screen` `planify`.
- **Planify AI guide** (`backend/src/planify/guide*.ts`, `POST /api/plans/guide`, Android `PlanGuideSheet`): a free model reads per-category monthly totals + credit labels (never merchants/transactions) and writes ONE multiple-choice question at a time; each option carries a whitelisted, clamped *effect* (setIncome, incomeHaircut, goalMonthly, commitment, estimate, categoryChange, savePercent, bufferPercent…) that `data/planify/PlanGuide.kt` applies with plain arithmetic, so the model never writes numbers. Amount-typed effects (`value: null`) open an amount field. Income comes from `income.ts` (salary-like credits this month > earlier months > largest credit). Low history (<2 months) = more questions + labelled estimates. `BackTest.kt` replays the draft against past months ("held in 2 of 3 months", one-tap raise); every bucket shows its `basis`. Falls back to fixed questions without consent / no model. `scripts/probe-guide.ts [rich|low] [Language]` exercises real models.
- **Smart matching** (`backend/src/planify/matching.ts`, table `plan_matches`, `POST /api/plans/[month]/match`): a bucket also counts spending the user CONFIRMED belongs in it (a category like Food in "Eating out", or a merchant like Zomato). Related-looking pairs are only suggested as Yes/No (`PlanView.matches`, shown by `MatchBox` under the bucket); No is never asked again; Yes counts in every month and teaches later suggestions; unrelated or vague ("Other") names are never suggested. `allocate()` computes spent per bucket. Android `PlanMath.bucketFor/belongs` honour `PlanView.aliases`. Smart categories: off-by-default toggle on the builder's Review step + a "Create category" button under a bucket whose category doesn't exist (`SmartCategories.kt`). Schema changes are applied by the user (never run db push).
- **Share + hold follow-ups**: Share on an assistant reply (`ui/share/ShareSheet`, `ExternalApps`) uses the system share sheet / `wa.me` / `mailto:`, plain text, amounts masked like Copy. Hold follow-ups (`ui/holds/FollowUpPanel`, used in the hold screen sheet AND inside the assistant chat as `FollowUpCard`): pick a contact with the system picker (no READ_CONTACTS; `ui/contacts/ContactPicker`), the phone/email are stored ONLY on the device (`SessionDataStore.holdContacts`, keyed by person name, cleared on sign-out) and never sent to the server or AI; `data/contacts/Outreach.kt` builds `wa.me` / `smsto:` / `mailto:` links and normalises numbers. A draft is ALWAYS written and shown first (AI via `POST /api/holds/message`, checked by `holds/message.ts#checkDraft`; else `FollowUpTemplates` from translated strings); only "Yes, send" opens the other app, the user taps Send there. Assistant tool `prepare_followup` (tier propose) only starts the card. `<queries>` in the manifest lists WhatsApp + mailto/smsto. No DB changes.
- **Reply / "Use as reference" on assistant answers**: the reply icon puts the answer above the input as a quote (`ReferenceBar`); the next message is sent with `reference` (`POST /api/assistant/chat`), which `loop.ts#quotedReference` fences in `<replying_to>` in front of the user's words (data, not instructions; the system prompt has a section for it). The quote is saved with the user message (`chat_messages.quote`, DB v3) and shown in their bubble. Quick chips: explain simply / shorter / compare with last month.
